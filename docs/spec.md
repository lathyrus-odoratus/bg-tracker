# 桌遊機制圖譜 規格

以「機制」為中心的桌遊知識圖譜：這款遊戲跟哪些遊戲有關，該怎麼教？
原始概念規劃（2026-10-25）的內容整理在這份文件，後面的決策以這份為準。

## 核心概念

- 桌遊與機制是多對多，首頁用圓形關係圖攤開
- 從遊戲找到它的機制，從機制找到用它的遊戲
- 每位使用者有自己的遊玩紀錄與想玩清單
- 為一款遊戲建立教學 roadmap，從熟悉的遊戲一步步走到目標遊戲

## 已定案的決策

| 主題 | 決策 | 理由 |
| --- | --- | --- |
| 圓形圖 | 不做 hierarchical edge bundling 的階層；遊戲右半圈＋機制左半圈（依名稱排序），hover／鍵盤 focus 點亮相關連線，預設線條調淡；觸控時第一次點亮、第二次進入。詳細資料顯示在圖上方的資訊列，不用浮動小卡（會遮住節點） | 主要用法是 hover 查詢，交錯不影響閱讀；不用多維護「機制分類」。依共現排序之後需要再加，不影響資料模型 |
| 身分 | 整個網站都要 Discord 登入，沒有匿名瀏覽；未登入一律導到登入頁，登入後回到原本的頁面 | 只給成員使用（2026-10-25 從「可匿名瀏覽」改成全站登入） |
| 遊玩紀錄 | 必須登入才能新增；第一版只有 BGA 紀錄 | BGA 視為資料來源 |
| BGA 紀錄登錄 | BGA 沒有 API：登入的使用者貼上對局網址，取出 table id，再選遊戲、時間、參與者（BGA 名稱）、名次與分數 | table id 唯一，同一桌只會登錄一次 |
| 參與者 | 只存 BGA 名稱；沒綁定的人也照記 | 綁定後過去的紀錄自動連上，不用補資料 |
| BGA 帳號綁定 | 管理員手動指定 BGA 名稱 → 使用者（不分大小寫，一個名稱只對一位） | 避免冒用。第一版管理員只有專案擁有者 |
| 管理員 | `ADMIN_DISCORD_IDS` 裡的人登入時升級成 admin（只升不降） | |
| 部署 | `bg-tracker.miao-bao.cc`，hobby-infra 的 Dokploy；push 到 main 由 CI 自動部署；repo `lathyrus-odoratus/bg-tracker`（public） | 和其他個人服務同一套流程 |
| 玩過 | 有遊玩紀錄，或自己標了「玩過」都算；玩過幾次、上次遊玩只從遊玩紀錄算。有紀錄的不能取消玩過 | 遊玩紀錄的輸入還沒做，先讓大家能自己標（2026-10-25） |
| 重度 | 每人替每款遊戲評一個重度（複雜度）1.0–9.9、間距 0.1，可以改、可以取消；顯示平均（小數一位）與人數。存成整數十分位（10–99） | 之後做相似度、排序可以用 |
| 新增遊戲 | 成員只能用 BGA 代號新增（名稱、人數、BGG id 由 server 向 BGA 查），標記「需要 admin review」；admin 確認後拿掉標記（只是確認，不影響顯示）。admin 的完整表單照舊，不需要 review | 讓大家能補遊戲，又不會亂填名稱 |
| 手動紀錄 | 第一版不做；`plays.source` 保留擴充空間 | 之後加 `manual` 來源，參與者要能直接指向使用者 |

## 資料模型

見 `apps/server/src/db/schema/`。

| 表 | 內容 |
| --- | --- |
| `users`、`user_identities`、`sessions` | 使用者、Discord 身份、登入 session（只存 token hash） |
| `games` | 名稱（不分大小寫唯一）、人數、時長、BGG id |
| `mechanisms` | 名稱（不分大小寫唯一）、說明 |
| `game_mechanisms` | 遊戲 × 機制 |
| `external_accounts` | BGA 名稱 → 使用者，記錄由誰指定 |
| `plays` | 遊戲、時間、來源、外部 id（BGA table id）、登錄者 |
| `play_participants` | 一場的參與者（BGA 名稱）、名次、分數 |
| `wishes` | 使用者 × 想玩的遊戲 |

- 「玩過幾次、上次遊玩」不存，一律從 `plays` ＋ `play_participants` ＋ `external_accounts` 推出；「玩過」另外可以自己標（`played_marks`）
- 學習路線（roadmap）的表還沒建，等下面的待決問題確定

## 頁面

| 頁面 | 內容與互動 |
| --- | --- |
| 首頁：圓形關係圖 | Hover 遊戲：小卡顯示名稱、我玩過幾次、上次遊玩、我想玩？，並點亮它用到的機制。Hover 機制：點亮使用它的遊戲。點擊進入詳細頁。旁邊放 Top K 大家想玩 |
| 遊戲 index／遊戲頁 | 遊玩紀錄、機制、誰想玩、誰玩過、相關 roadmap |
| 機制 index／機制頁 | 名稱、說明、使用此機制的遊戲 |
| 玩家頁 | 遊玩紀錄、玩過的遊戲、想玩清單 |
| 登錄 BGA 紀錄 | 需要登入 |
| Roadmap index／Roadmap 頁 | 從目標遊戲往下的樹，每個機制是一個區塊，區塊再接後續機制；「在圓形圖上播放」是加分展示 |
| 管理 | 遊戲、機制與對應；BGA 帳號綁定 |
| 留言板 | 新的在前，一次 25 則，「載入更多」載入更早的。留言與回覆同一層，每則有編號、作者、時間、回覆哪則（選填）、內容；作者可以編輯，每一版都留著可以回看 |

## 待決

- **Roadmap 區塊列的遊戲**：自動列出所有有此機制的遊戲，還是由人挑 1–3 款「建議用這款學」？（傾向人挑）
- **Top K 大家想玩**：要不要排除大家都玩過的？
- **玩過之後**：要不要自動從想玩清單移除？

## 後期功能

- **相似度**：以共用機制為主，再加入重量、時長、人數等維度（`games.bgg_id` 用來補資料）
- **BGG XML API**：管理員輸入 BGG id，帶入名稱、人數、時長、重量與機制（機制名稱是英文，要對應到我們的中文機制，或只當參考）
  - 需要先在 https://boardgamegeek.com/applications 註冊 non-commercial application（審核可能要一週以上）
  - token 只放 server（環境變數），請求帶 `Authorization: Bearer <token>`，網域是 `boardgamegeek.com`（不加 www）
  - 結果存進資料庫，不要每次瀏覽都打 BGG；請求數盡量少
  - 公開網站要放「Powered by BGG」logo 並連回 BGG
- **BGA 遊戲名稱對應**：之後若能半自動匯入，再加遊戲別名表
